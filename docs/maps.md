## 2. The tables

- **Map pointer** `$C8:7000 + 2*m` (word, offset in bank `$C8`) -> 8 header bytes, then 8-byte object records up to the next map's pointer. Maps whose pointer equals the previous one have no header (0-7 and many others): 394 of the 512 ids have one (id 511 is an all-0xFF end marker) [V].
- **Piece list** `$C8:5000 + 2*m` -> records up to the pointer of map m+1; **event list** `$C8:4000 + 2*m` -> words up to the next map's [V].
- **Transitions** `$C8:3000 + 4*n`: word 0 bits 0-8 = target map, bits 9-15 = start tile X; byte 2 bits 1-7 = start tile Y, bit 0 = the party starts on layer 2 (`$C0:CA3F` rotates it into `$BF`; set for every house door: inside a house the heroes walk on the layer-2 map and attributes, and the door tiles are layer-2 trigger ids) [V: hero walked down to the 0xBF door of map 259 on layer 2 with the real routine]; byte 3 = flags, low 5 bits the **exit code** (0 none, 1 up, 2 down, 3 right, 4 left, higher = other walk counts; `docs/cutscene-engine.md` 13.2) [V]. Heroes are placed at `(16 * X + 8, 16 * Y + 10)`.
- Object-record flags, music and event ids are read through the event VM (`docs/cutscene-engine.md`).

## 3. Tile layers: pieces [V]

A map is built from **pieces**: rectangles of tile ids pasted into a 64 KiB work buffer with 128 ids per row (`$7F:0000` = layer 1, `$7F:4000` = layer 2). `$C0:CB90` walks the piece list of the map:

- Record = 5 bytes: flag index `f`, range byte (min << 4 | max), `p2`, `p3`, `p4`. The first record of each layer has a prefix byte 0xFE (layer 1) or 0xFF (layer 2) in front of it (6 bytes in all); 0xFF switches the destination to layer 2 for the rest of the list.
- The record is used when `min <= flag[f] <= max` (whole byte of the event flag area `$7E:CF00 + f`). A new game has all flags zero. Event op 0x0A runs the walk again (`docs/cutscene-engine.md`), so these pieces are the doors, walls and bridges that events open. In the area built so far: 131 (flag 0x10 >= 6), 29 (0x5E), 30 (0x5F, three steps), 139 (0xA4, 0xA5, 0xA6), 135 (0xA7), 265 (0x13); the Godot builder stores, per flag and value range, the cells and solid tiles that change (`piece_variants`).
- Destination x = `p3 >> 1`, y = `p4 >> 1` (buffer offset `y * 128 + x`, +0x4000 for layer 2). Piece id = `p2 | (p3 & 1) << 8 | (p4 & 1) << 9`.
- Piece location: `$CD:0004 + 2*id` is a pointer; the bank is `$CD` below the word at `$CD:0000`, `$CE` below `$CD:0002`, `$CF` below `$CD:0004`, else `$CC`. Offsets run on past 0xFFFF into the next bank.
- The **first** piece of layer 1 that passes its flag test sets the map size: width = `(d0 >> 1) + 1`, height = `(d1 >> 1) + 1` tiles of its first two bytes; map pixels are 16 times that (`$C0/$C2`). The first piece of layer 2 sets the layer 2 size [V: 394 maps, native = loader].

Piece body (`$C0:CD93`): bytes `d0`, `d1`; if `d0 & 1` or `d1 & 1` a table of up to 8 sub-pattern entries follows (`dims` byte = (height - 1) << 4 | (width - 1), then the entry's own stream up to a byte >= 0xF8; 0xFF ends the table). Then the stream fills the piece in raster order, width x height cells in the 128-wide buffer. Opcodes:

| byte | effect |
|---|---|
| 00-BF | literal tile id |
| C0-DF | repeat the cell `n` cells back (n = ((b >> 3) & 3) + 1, wrapping to the previous row) `(b & 7) + 1` times |
| E0 + B | copy `(B & 0x7F) + 1` cells from the row above (two rows above if B bit 7) |
| E1-E7 | copy `(b & 7) + 1` cells from the row above |
| E8-EF + B | LZ copy: from `((b & 7) * 2 + (B >> 7)) + 1` cells back, `(B & 0x7F) + 1` cells, one at a time |
| F0 + B | run of `(B & 0x7F) + 1` cells counting up from the previous cell (down if B bit 7) |
| F1-F7 | the same counting up, `(b & 7) + 1` cells |
| F8-FF | the cell is left empty and sub-pattern `b & 7` is pasted there after the main stream |

`tools/map_native.py` implements this. `verify` runs the native decoder and the real loader for the 394 maps and compares layer 1, layer 2, size, graphics, palette and attributes (section 12).

**Marker tiles.** After the pieces, `$C0:D037` calls `$02:B517` for every cell whose attribute entry has bit 7 of b1 set: the cell gets a new tile id `0xC0 + n` (n counts in row-major order, per layer) and the attribute entry and the four tilemap words of the old id are copied to the new one. The new ids are the **trigger tiles** of section 8; they look exactly like the original tile. `map_native.apply_markers` reproduces it [V].

## 4. Graphics, palette, tile set

- **Characters** (`$C1:F413`): the set is a list of 3-byte records at `$CC:E27E` (word, count - 1). Word bits 15-13: 000-011 = 2bpp tiles of 16 bytes from pool 0 with planes 2 and 3 filled with 0x00/0xFF (bits 14 and 13); 100/101 = 3bpp tiles of 24 bytes from pool 3, plane 3 filled by bit 13; 110 = 4bpp tiles of 32 bytes (pool 6); 111 = units of 64 bytes (pool 9). Bits 12-0 = first tile in the pool; pool pointers at `$CC:E270` (3 bytes each). The tiles go to VRAM address 0 in order (864 characters, 27,648 bytes for every set seen) [V native = loader]. A record may cross a bank boundary; the loader splits the DMA there.
- **Palette** (`$C1:F62D`): BG rows 1-7, colours 1-15 from `$CC:8000 + 0xD2 * set`; row 0 only holds the backdrop (colour 0) and two window colours [V].
- **Tilemap words**: `$7F:C000 + 8 * id` (layer 1) and `$7F:C800 + 8 * id` (layer 2) hold the four SNES tilemap words of the 16x16 tile id: top-left, top-right, bottom-left, bottom-right (character number bits 0-9, palette bits 10-12, priority bit 13, flips 14-15). Rendering layer 2 (BG2) below layer 1 (BG1) with the priority passes BG2 p0, BG1 p0, sprites, BG2 p1, BG1 p1 reproduces the public maps (section 11) [V].
- **Attributes** (`$C2:A043`): 4 bytes per id at `$7F:B800` (layer 1) and `$7F:BC00` (layer 2). Header byte 2 selects 384 bytes at `$CB:0400 + 0x180 * set`: 192 indexes into the 4-byte entries at `$CB:0000` for ids 0-191, 192 more for the alternative set [V native].

## 5. What the layers mean in play

BG1 (layer 1) carries the cliffs, trees, buildings and the tile attributes that matter for walking; BG2 (layer 2) is the ground (grass, water, floors). An object walks on one of the two layers: `E00B` bit 7 clear = the tile ids and attributes of layer 1, set = those of layer 2 (house interiors are entered on layer 2, section 2). The bit is set by the transition and toggled by the layer-switch tiles (`b0` bit 3). The log bridges of the first area do **not** use it: they are built from floor heights and pass-through tiles on layer 1, and the drawing order of the objects on them comes from `b1` of the tile (section 14) [V].

## 7. Collisions [V]

The hero routine `$C0:D5C0` -> `$01:B93E` reads the tile id of the hero's layer (layer 1 unless `E00B` bit 7 is set, section 14) under the leading edge of the 13 x 9 box (`docs/hero-movement.md` section 7) and its attribute entry (b0, b1, b2, b3):

- `b0 & 7 == 3`: solid. `tools/map_collision.py grid 129`: of 2,815 solid tiles, 2,811 stopped the hero in all three probe directions, 4 in two [V].
- `b0 & 7` 0 and 2 never blocked (1,073 tiles) in the grid probe, which starts every hero with the height of its own tile. **Floor heights** [V: `tools/map_collision.py heights`, synthetic tiles in map 130]: at every step the hero's `E00B & 3` takes the type (0, 1, 2) of the tile under it (types 4-7 keep it: section 14), and a step from a type-1 tile onto a type-2 tile, or from 2 onto 1, is refused; type 0 (ramps, stairs, plain ground) connects both. So the edge between neighbouring type-1 and type-2 tiles is a wall in both directions, matching `((t ^ E00B) & 3) == 3` read at `$C0:D876-D88C`. The first rooms have such edges in 16 (202), 19 (39), 145 (25), 144 (15), 136 (14), 130 (2), 159 (1); none of them has a tile with `b0` bit 3 on the layer the party walks on. Bridges: section 14.
- `b2` high nibble 1 with low three bits 4-7: **diagonal half tiles** (`$01:BC37`). Measured on a single tile (`map_collision.py shape 0x12 0x14` ...): 4 = lower-left triangle (corners (0,0), (0,16), (16,16)), 5 = upper-right ((0,0), (16,0), (16,16)), 6 = upper-left ((0,0), (16,0), (0,16)), 7 = lower-right ((16,0), (16,16), (0,16)) [V]; the cliff and ledge edges use them.
- `b1` bit 4: **return door**. When the controlled hero stands on such a tile (`$C0:D688` sets `E04A` = 0x80), `$C0:B60E-B62D` jumps to `$C0:BBD1`: `$01:CCF5` copies the place saved at the last map transition (`$7E:CE00` -> `$CD00`: camera, cached object records, map id at `$CD08`) and the loader runs with `$E8` = 0x80, which restores the camera from `$CD00` (`$01:CD17`); party placement runs separately in the loader. Every map transition saves that place first (`$01:CBCF` called from the transition starter `$C1:E7CF`). Non-heroes cannot step on these tiles. This is how the party leaves most house rooms: the rooms of map 257/258 entered by transitions 88, 89, 91 have no trigger tile, only two return-door tiles at the doorway [V: real frame loop, hero walking down out of the room reloads the saved map]. Bit 6 lets AI partners walk on trigger tiles; bit 7 marks an exit/trigger tile (section 3) [C].
- `b2` 0x30-0x3F: moving floor (river current) `docs/hero-movement.md` 5 [V there].
- **Cuttable tiles**: `b2` 0xC1, 0xC2, 0xC8 mark a tile that a weapon swing replaces by the tile id in `b3` (the write is done by `$01:D3F7`). Measured with the real frame loop and a swing of each weapon type at two such tiles (`tools/map_cut.py`, weapon rows 0, 9, 18, ..., 63): 0xC1 is cut by the sword, 0xC2 by the axe, 0xC8 by the sword and the axe; glove, spear, whip, bow, boomerang and javelin cut none of them, 0xC4, 0xCC, 0xD0, 0xE0, 0xFF nothing [V; the whip and the thrown weapons were tried from the same spot only]. The bushes of the Potos Falls (tile 5: b0 0x13 solid, b2 0xC8, b3 0x5F -> tile 0x5F, a floor) close the way east to map 129 until the sword cuts them. The replacement lasts until the map is loaded again.
- Non-player objects cannot enter trigger tiles (`$01:B9A9`) [C].

## 8. Exits, entries, events

- A hero standing on tile id `t >= trigger_base` (`0xC0 - (header byte 3 & 3)`) starts event-list entry `(t - trigger_base) + e`, `e` = 1 if header byte 3 bit 2 is set (the first word is the map entry event) (`$C0:B63A`, only for the controlled hero) [V: maps 245/246 list `[0x428, 0x429]`, 131's 203 painted exit tiles].
- Entry event = first word, run by the loader (`$C0:BEAA`) when header byte 3 bit 2 is set; it starts the music (event `0x7xx` = `SOUND` 1 with id xx) and map-specific scenes.
- An event word >= 0x800 and < 0xC00 is a **map transition** (table of section 2); 0xC00 warp inside the map; below 0x800 a script that may contain `MAP_CHANGE` (flag dependent branches, dialog). `map_tables.py map ID` lists, per trigger id, the event and the transitions its script can reach.
- Painted trigger ids (0xBD-0xBF) form the long exits at map borders (131 has 203 tiles of 0xBD) and the doors of houses (on layer 2); marker clones (0xC0+) are single tiles (passages, stairs, signs).
- The event list is indexed without a bound: a map with a short or empty list reads the words of the next map's list (257 has none and its trigger tiles use the words of 258) [C, `$C0:B667`].
- Trigger events seen in the first rooms: plain transitions; **signs** (events 0x600-0x60C: one text block and `GOTO 0x5FF`); **story gates** (`IF_FLAG_RANGE` on flag 0x10, the Potos story counter, e.g. 0x104/0x102 in map 128 push the hero back with a dialog until the story moves on); scripted map changes (0x45A in map 19). NPC records carry the talk events (flag 0x10 or 0x12 ranges choose which villagers exist at each story step; 0x11 for the crossroads, 0x0A for the Potos Falls actors). No chest, switch or item-pickup object exists in these rooms; monsters respawn from the records at every map load because the spawner runs on each load and tests only the record flag [C].
- Scene rooms: the opening room 256 has no exit tile; its entry event (0x100 -> 0x400 with flag 0 = 0) performs, in order, the transitions 207, 206, 205, 204 (prologue pictures), 0 (back to 256), then event 0x106 and transition 130 to map 128 (`map_dump.run_changes`, flag-aware walk of the script) [C for the walk, V for the opcodes]. Map 133 (camp with fire pit and huts) is a scene room: its only entry, transition 4, is performed by event 0x4E8 (started by the trigger event 0x11F of map 16 when flag 0x11 >= 11 and flag 0x2E = 0); the same script moves the actors in 133 and leaves with transition 105 back to map 16 (10, 54), then sets flag 0x2E = 1 so it does not repeat. `map_dump.scene_exits` lists, for every map, the transitions scripts perform right after entering it. Transition 150 (tile 0xC1 of 133) to map 139 belongs to a later story step.
- Music: first `SOUND` command with command 1 of the entry-event chain; maps without an entry event keep the music of the previous map (128, the Potos Falls) [V for the event decode].

## 9. Animation [V]

`$01:B033` (scroll/HDMA table `$7F:8000`), `$01:BFE0` (character animation records at `$7F:8200`, 16 bytes each, uploaded by the NMI) and `$02:BAD6` (palette cycling records at `$7E:D200`) run every frame. `MapEnv.animation_phases` runs them with the NMI upload over a window of a loaded map.

**Scrolling characters** [V]: the loader's animation set-up (`$01:B1D0-B267`) reads the original characters of every scroll record back from VRAM into WRAM with a read DMA (`$2115` = 0x80, a dummy read of `$2139`, then channel 7 in mode 1 from B-bus `$39`, 192 bytes): on map 128 characters 0x33D, 0x34D, 0x1B1, 0x1B2 go to `$7F:8400`, `$7F:8800`, `$7F:8C00`, `$7F:8E00`. A dispatcher on the record type (`$01:B2AD`: types 0-3 shift routines, 4 = `$B687` only replicates the block with `MVN`, 5 = `$B5AD` generates shifted copies and replicates them, 6 = `$B411`/`$B478`) builds 0x400-byte strips at `$7F:8600`, `$7F:8A00`, ... and the NMI uploads 64 bytes of a strip every 8 frames, moving the source by 0x40 (16 positions, a 128-frame cycle): the dark waves of BG1 over the river of Potos Falls. Tools before this read emulation (`rip_hero_anims.PpuCpu` ignored B-bus to A-bus DMA and `$2139` reads) left the strips empty, so those characters were blank in every phase; the read port is now emulated with the SNES prefetch latch (setting VMADD loads it, reading the incrementing byte returns it, reloads it from VMADD and then increments), with which the WRAM copies equal VRAM from the set address.

**Periods** [V, map 128, 64 phases 8 frames apart]: 28 characters repeat every 4 phases (32 frames), the 6 scroll characters every 16 (128 frames), palette colours every 4 (8 colours) or 15 (5 colours, 120 frames); a tile combining a 4-phase character with a 15-phase colour repeats every 60 phases. Characters 0x360-0x363 change only once in the window (phases 9-11): an occasional animation started at other times, not a cycle [C: trigger not decoded]. The Godot builder captures 64 phases and gives every tile the shortest period its pictures repeat with (or its most frequent picture when they never repeat).

## 10. Object records (8 bytes) [C; V for the position formula and ids of maps 245/246/253]

`+0` flag index, `+1` min<<4 | max, `+2` x tile (bits 0-6), `+3` y tile, `+4` bits 7-6 facing (0 up, 1 down, 2 left, 3 right), bits 5-4 layer, `+5` object id (0x00-0x56 monsters; 0x57-0x7F bosses; >= 0x80 NPC kinds, chests and switches among them), `+6/+7` event word (contact/talk event = low 12 bits). ## 14. Layers, bridges and sprite priority [V unless marked]

Tool: `tools/map_layers.py` (real frame loop of `rom_screen.ScreenWorld`: frame body `$C0:B08C`, NMI with the OAM upload, pad held in `$4219`; the party is put on any tile of any map by replacing the target of transition 130). Every row tagged [V] below was produced by that tool; the OAM entries are attributed to their object by the `$0014` tag of `rip_boss.OwnCpu`. Runs: `bridges` (maps 128 and 130, all three log bridges), `opening` (event 0x106 to the end, hero in the water of map 128), `priority` (synthetic ground, `b1 & 7` = 0..7), `switch` (synthetic `b0` bit 3 tile), `scan` (attribute classes of every map).

### 14.1 What the object keeps

| field | meaning | written by |
|---|---|---|
| `E00B` bit 7 | layer: 0 = tile ids `$7F:0000` + attributes `$7F:B800` (layer 1), 1 = `$7F:4000` + `$7F:BC00` (layer 2). Selects the tiles used for the collision and for the tile under the object (`$C0:D74F-D771`), the camera word pair used for the screen position (`$A8/$AA` or `$AC/$AE`, `$C0:E410`) [C] | transition byte 2 bit 0 (section 2), object record layer bits (`$C0:DED9`) [C], switch tiles |
| `E00B` bit 3 | "standing on a switch tile" latch | switch tiles |
| `E00B & 3` | floor height 0, 1, 2 | every move |
| `E00B` bit 0 | also the sprite group: objects with bit 0 set (height 1) are emitted to OAM before the others (`$C0:E8D7` builds two lists, `$0540` for bit 0 set and `$0500`, `$C0:E39B` emits `$0540` first) | |
| `E08E` | ground priority code 0-7 (14.4) | every move |

All of it is updated by the same code for every object after a move that the collision allowed: heroes `$C0:D65D` -> `$C0:D890` (slots 0-2, `$C0:D5ED`), every other object `$C0:D229` -> `$C0:D74F` -> `$C0:D890` (slots 3 and up, `$C0:D1FE`) [C]; measured for the controlled hero, both AI partners and a Rabite (14.3).

### 14.2 The rules

**Tile under the object** (tile of the new position `(E002, E004)` on the object's layer, `$C0:D7F3-D88E`):

| attribute of that tile | `E00B` afterwards | `E08E` afterwards |
|---|---|---|
| `b0` bit 3 set, latch clear | `(E00B ^ 0x88) & 0xF8`: layer toggled, latch set, height 0 | unchanged (`b0` bit 2 is clear on every switch tile, so `b1 & 7` is taken as below) |
| `b0` bit 3 set, latch set | unchanged | as below |
| `b0` bit 3 clear, `b0 & 7` = 0, 1, 2 | latch cleared, height = `b0 & 7` | `b1 & 7` if `b0` bit 2 is clear and `b1 & 7 != 0`, else unchanged |
| `b0` bit 3 clear, `b0 & 7` >= 3 | latch cleared, height unchanged | unchanged when `b0` bit 2 is set (types 4-7); for type 3 as above |

`E08E` is written at `$C0:D69A-D6A6` (heroes) and `$C0:D2AF-D2BB` (others) [C; V: 14.4 shows the "unchanged" cases].

**Leading edge** (`$01:B93E`, `$01:BE15`/`$01:BC37`, each tile the 13 x 9 box enters, on the object's layer):

| `b0 & 7` of the entered tile | object height | result |
|---|---|---|
| 3 | any | wall |
| 1 | 2 | wall |
| 2 | 1 | wall |
| 1 or 2 otherwise, 0, 4-7 | any | free (only the diagonal shapes of `b2` 0x14-0x17 apply) |

Before the edge test, if the tile under the new centre has `b0` bit 3 the move is allowed with no edge test at all (`$01:B9E0`) [C]. In the whole ROM only `b0` values 0x15 (type 5, `b1` 0) and 0x16 (type 6, `b1` 0, map 60) occur with a type >= 4 (`map_layers.py scan`).

So a **pass-through tile** (type 4-7) can be entered from any height and keeps the height the object arrived with; whether an object is on or under a bridge is only its height.

**Ramp tiles** `b2` 0x20-0x2F: `docs/hero-movement.md` section 5 measured the effect (the walk along one axis loses frames and is deflected on the other axis) without knowing its use; they are the **bridge ramps and stairs**. 0x22 and 0x23 are the two ends of the log bridges of maps 128 and 130 (type 0, so they connect the land at height 2 with the bridge end at height 1); 0x21 is the common stair tile (8 cells in map 16, up to 84 in a map). Walking right over 0x22 moves the hero up (map 128: y 1082 -> 1076 while crossing (28, 67)), over 0x23 down [V for 0x22, C for the sign rule at `$C0:D391-D3AE`].

### 14.4 Sprite priority from the ground [V]

The sprite builder (`$C0:F6C0-F760`) starts every OAM entry of an object from its attribute byte `E08B` (priority 2 for the heroes and the Rabite, measured; map objects get 0x20 at `$C0:DF55-DF69` unless their record has `E03C & 7 >= 4`, which gives another value at `$C0:DF71` [C]) and changes the priority by `E08E`. The pieces whose frame-data flag is set (bit 7 of the piece's first byte, `$C0:F70E-F714`) are "upper" pieces; for a hero they are the upper 16 px (water run: entry at screen y 84 priority 3, entry at y 100 priority 2, with the hero position at y 114). The shadow (`$C0:E760`) takes `(E08E << 4) & 0x30`, or `E08B & 0x30` when `E08E` is 0.

Measured with the hero walking from a `b1 & 7` = 7 floor onto a 9 x 16 patch of synthetic ground (`map_layers.py priority`):

| `E08E` (= `b1 & 7` of the last tile that set it) | upper pieces | lower pieces | shadow |
|---|---|---|---|
| 0 (never stored: the code is kept) | - | - | - |
| 1 | 2 | 1 | 1 |
| 2 | 3 | 2 | 2 |
| 3 | 2 | 1 | 3 |
| 4 | 0 | 0 | 0 |
| 5 | 1 | 1 | 1 |
| 6 | 2 | 2 | 2 |
| 7 | 3 | 3 | 3 |

With `b0` = 0x15 (bit 2 set) every value 0-7 left the code at 7 (unchanged). In the 67 rooms of the Godot port the non-solid tiles carry only the codes 0 (keep), 2, 6 and 7 (layer 1: 3,934 / 30,222 / 18,726 / 6,650 cells, the 185 pass-through cells among the 0; layer 2: 356 / 767 / 51,531 / 25,165).

Mode 1 order, front to back: OBJ 3, BG1 high, BG2 high, OBJ 2, BG1 low, BG2 low, OBJ 1, BG3 high, OBJ 0, BG3 low. So:

- **Land** (code 7): the whole object is priority 3, in front of every map tile, including the high-priority tree tops and the log of a bridge (hero on a deck).
- **Water** (code 2): upper body 3 (clean), legs and shadow 2, behind the high-priority layer-2 water, which is translucent: only the legs look submerged. Measured at the end of the opening (`map_layers.py opening`: event 0x106 ends in map 128, hero 0 at (31,27) `E00B` 02 `E08E` 2, entries [3, 2, 2]; the two partners [3, 3, 2, 2] and [3, 3, 2, 2, 2]); walking down the river keeps the split.
- **Walls, log edge, house floors** (code 6): everything 2, behind high-priority tiles (hero under a bridge: the deck tile 0x78 is high in all four quarters, 0x88 in its upper half, so the log covers the hero).

The ground code is not recomputed from the tile under the object every frame: it is the last non-zero `b1 & 7` of a tile without `b0` bit 2 that the object moved onto. This is what lets the same deck tile show one hero in front of the log and another behind it.

**Order between sprites**: with a Rabite overlapping the hero, the Rabite's entries came first (in front) at heights 2/2, 1/1 and with the hero at 2 and the Rabite at 1, whatever their y; with the hero at height 1 and the Rabite at 2 the hero came first. So objects at height 1 (an `E00B` bit 0 group, 14.1) are drawn over the others; The earlier frame harness showed the monster ahead of the hero in both y orders. A later native proof of `$C0:E8D7` establishes ascending unsigned `E022` within each generated list, with equal depths retaining descending actor-slot order. This proves the list boundary; sprite-piece emission and final OAM ordering still require their own proof (see the complete sprite workspace/order section below).

### 14.5 The layer switch (`b0` bit 3) [V on a synthetic tile]

`map_layers.py switch`: map 130, tile id 0xB0 with attribute `18 07 00 00` (type 0 + bit 3) at (10, 40) on both layers, a wall on layer 1 only at (10, 38), a wall on layer 2 only at (12, 40):

- On layer 1, walking right along row 38 stops at the layer-1 wall (9, 38).
- Walking up from (10, 42): (10, 41) `02` -> switch (10, 40) `88` (layer 2, latch, height 0) -> (10, 39) `82` -> (10, 38) `82`: the layer-1 wall is not seen any more -> (10, 36).
- Back down: (10, 39) `82` -> switch `08` (toggled back to layer 1) -> (10, 41) `02`.
- Up onto the switch and then right: `88` -> (11, 40) `82`, stopped by the layer-2 wall at (12, 40); left back over the switch `08` -> `02`.

So each fresh entry onto a switch tile flips the layer (it is a toggle, not "go to layer 2"); the tile must exist on the layer the object is on when it steps on it. An AI partner stepping on a switch tile copies bit 7 from the hero at `$BA` instead of toggling (`$C0:D890-D8AD`); measured with a row of switch tiles and both partners following: the code ran for slots 0x200 and 0x400 with `$BA` = 0 (the leader) and both ended on layer 2 like the leader [V]. Objects of slot 3 and up toggle like the controlled hero [C].

Where switch tiles are (`scan`): layer 2 of maps 0, 14, 63, 102, 104, 131, 132, 144, 153, 168, 194, 197 (the party enters all of them on layer 1, so these cells are not under its feet unless something else sets bit 7), layer 1 of maps 14 and of the house maps 257, 258, 259, 261-263, 279-281, 298, 299, 333, 335, 341, 342, 376 (entered on layer 2: the tiles 0x70/0x71 `18 07` beside the entry point, e.g. 259 (18, 15) and (21, 15) next to the start (20, 14), are on the other layer). No walk in the first rooms reaches one [C: from the entry layers; events that set `E00B` were not searched].

**Other effects of `E00B`** [C]: the facing test of the hero against interactive objects (`$C0:B851-B959`, probably talk/examine) requires the same bit 7 and refuses heights 1 against 2; boss mode (`$ED` bit 7) lets only objects with `E074` bit 7 collide with tiles (`$C0:D29A`).

### 14.7 Porting rules (generic)

1. Per object keep `layer` (0/1), `latch`, `height` (0/1/2) and `ground` (0-7).
2. After every accepted move, look up the tile under the object's position on its layer and apply the first table of 14.2.
3. Refuse a move when the box's leading edge enters a tile of type 3, a type-1 tile at height 2 or a type-2 tile at height 1 (plus the diagonal shapes); skip the edge test when the tile under the new centre is a switch tile. Types 0 and 4-7 never block.
4. Draw the object with the priorities of the table of 14.4 for its `ground` code, upper pieces separately from the lower ones; priority 3 = above both high tile layers, 2 = between the low and the high tile layers, 1 = below the BG1/BG2 tiles (above BG3 high), 0 = below everything but BG3 low.
5. Sprites of height-1 objects go above the other sprites.
6. On a map load the code is not reset; `$C0:F088-F0AB` copies `E010`, `E00B` and `E08E` of the hero at `$D4` to the three heroes [C, the caller was not identified]. Taking the code of the start tile is an approximation (inferred, not measured).

Open: the order of sprites inside a height group; the `E08B` base priority of map objects whose record has `E03C & 7 >= 4`; whether any event sets `E00B` bit 7 so that the switch tiles listed above are reached; NPC kinds were not exercised (same code path as the Rabite [C]).
