Goal (user request 2026-10-17): romhack-style battle options that work on the US ROM, the Spanish Magno translation and
randomizer output (Ancient Cave, Chaos, ...), next to the companion direct control: no wait between weapon attacks,
monsters that do not flinch unless hit by magic or a critical, faster and configurable charge build-up, and similar.

### 1.2 Attack recovery (swing lock)

`E01C = 0x20` during a swing, set at `C0:B29F`, cleared by the animation script; 4 or 5 animation steps of 5 frames

### 1.5 Critical hits

`C0:532C`: forced crit if `E1AE & 0xF0` (counter, `-0x10` per hit); else if `E1ED == 0`: chance `E196` (x2 if defender
`E190 & 0x10`) `+ 10` for hero slot 1 or `+ 5` for the other heroes, critical iff `rnd(256) < chance` (byte wrap);
critical = `JSL $C05990` (notice) then `ASL $89` (damage x2, `C0:537C`). Immediates: `C0:5354` `ADC #$0A`, `C0:535E` `ADC #$05`
(operands at `+1`). `docs/rom-combat.md` 4.3. **[V new]** vanilla crit rate 1.7-2.5 % at base 0 (+5/256); with the bonus set to 60 it is 21 %.

### 1.6 Buffs, debuffs, statuses, damage formula

Already documented, not changed in round 1: buff bits `E1B0` (01 DEF+, 02 DEF-, 04 EVA+, 08 EVA-, 10 ACC+, 20 ACC-, 40 ATK+, 80 ATK-,
Speed Up = 04+10), timers `E1B2-E1BC`, Saber `E1AE/E19D`, barrier `E1B1` bit 4 + `E1BF`, immunity `E1AA`, status words `E190/E199`:
`docs/rom-combat.md` sections 4.3, 4.6, 7, 12, 16 and the pipeline notes (`combat_physical_damage`, `combat_status_application`).
Damage caps: 999 at `C0:4022`, `4060`, `5056`, `5275-527A`, `52D8-52DD`.

### 1.7 Facts that matter for patching [V new]

* Magno (Spanish) has the combat block relocated: a pure shift of **+0x17 from `C0:4EBC` to about `C0:63FF`** (`4EBC -> 4ED3`, `532C -> 5343`,
  `5372 -> 5389`; the `JSL $C05990` operand becomes `$C059A7`). Everything else used here (`B330`, `F925`, `1CACD`, `2C23A`) is at the vanilla offset.
  The tool finds the three relocated sites by instruction signature (see `resolve()`).
* Randomizer ROMs (4 MiB) keep bank C0-DF at the vanilla offsets and put their routines at `0x200000+`. The 0xFF run
  `DC:0540-08FF` (file `0x1C0540`, 960 bytes) is identical in vanilla, Magno and all five randomizer modes: it is the free area used here.
* Checksums: vanilla and Magno have a valid SNES checksum, randomizer ROMs keep the vanilla value (invalid). The tool recomputes it only when the input was valid.

## 2. Patch mechanism

### 2.1 (a) ROM patches as data

`som_gameplay.py apply --rom IN --options opts.json --out OUT` copies the ROM (copier header kept), checks each record's
expected `before` bytes, writes `after`, fixes the checksum (auto/always/never) and writes only outside the repository.

* Option file: JSON `{"options": {...}}` (`gameplay_options.json` lists every key with its vanilla default). Everything at default = no records = **byte-identical copy**.
* `plan --options f --rom R` prints every record (`offset`, `snes`, `before`, `after`, option, note) and whether the ROM matches (`ok` / `already` / `conflict`).
* `ips --options f --out x.ips` exports the same list as a standard IPS (vanilla layout, headerless offsets, no checksum). Magno needs `apply` (relocated sites).
* `verify --rom R --patched P --options f` proves that P differs from R only inside the planned records (+ checksum bytes).
* Conflicts: a record whose bytes are neither vanilla nor already patched is a conflict. `--on-conflict error` (default) aborts with
  the offending hack named; `skip` drops the whole option (and its routines) and reports it. Options are independent.
* Routines are assembled by a small label-aware emitter in the free area `DC:0540`; the whole set (all options, `heavy`) uses 145 of 960 bytes.

### 2.2 (b) Runtime injection (companion, no ROM change)

What a WRAM-only hook (`tools/companion/direct/som_direct.c` style, per-frame writes after `retro_run`) can do, measured on the UNPATCHED vanilla ROM
(`work/exp_runtime.py`):

| Option | Runtime route | Result |
|---|---|---|
| instant recharge | write `E1ED = 0` after each frame | 75 swings in 1500 frames, none penalised; same as the ROM patch |
| faster charge | add to the build-up counter `E01A` after each frame | stage 1 at frame 47, 34 frames per stage (vanilla 90) |
| no flinch for non-magic hits | after each frame, if a monster entered the hurt state and `E1F0 < 0x80`, restore `E011/E010/E190/E1B4/E060` from the previous frame | 0/20 weapon hits flinch, 20/20 magic hits flinch |
| critical-aware flinch, crit chance bonus | not possible: the crit decision is not stored anywhere and the RNG call is inside `C0:532C` | needs the ROM patch |

The NMI stub area `7F:FF90-FFFF` (112 bytes) is free, but ROM code cannot be redirected from WRAM, so the routines of 2.1 cannot be moved
there. Recommendation: ROM patch for everything (it travels with the ROM on Thor, 3DS, PC), WRAM hook only as a fallback for the two simplest
options on a ROM that cannot be patched. The patch writes nothing at `7F:FF90+`, so the direct-control stub is not touched by it.

## 6. Regression risks and limits

* **Boss and scripted fights**: bosses (`E1FB & 0x40`), heroes and lethal hits bypass the gate, so boss flinch timing is unchanged.
  Ordinary monsters that are part of a script (for example walls, gates, scripted "kill N enemies" rooms) lose their hurt animation; the
  engine only relies on HP, which is untouched. Not tested on every map.
* **Balance**: `never`/`strong` make monsters keep attacking while hit (no stun lock), `instant` removes the half-damage/no-crit window. Together with
  `charge_speed=instant` stage 8 is reached 8 frames after the charge starts. Lower values or `fast` are the playable range.
* **AI partners** use the same routines (they charge faster and recharge faster too).
* **Crit mark with zero damage**: fixed in round 2 (section 8.3): the zero-damage path clears the mark.
* **Monster poison/status ticks** pass through the gate with the last damage source (by construction, not run): after a magic hit they flinch like in vanilla, after a weapon hit they do not.
* **Checksum**: patched vanilla/Magno images get a new valid checksum; if the input checksum was invalid it stays invalid.
* **Not verified**: real hardware, a full playthrough, 3DS/Thor builds, a live companion session (only the library-level test, 6b and 8.2). Boss and generated-ROM
  combat were run in round 2 (section 8.1); they use scripted fixtures, not a human play session.

### 8.3 Fix: zero-damage critical under `strong`

A critical whose damage is reduced to 0 by the guard went through `JSL $4E6B` (zero-damage path at `5176`) and kept the mark, so the next weak hit on that monster flinched.
The path is now hooked and clears the mark. Test (hero attack poked to 0 so the damage is truly 0): off: weak hit after it flinches; with the old routine: mark stays 1 and the next weak hit flinches;
with the fix: damage 0, mark 0, next weak hit does not flinch.

### 8.4 Self-check: foreign use of the free byte `+0x16B`

`scan_mark_use(body)` looks for instructions whose operand is `$016B` (absolute, absolute indexed, `LDX/LDY/CPX/CPY #$016B`) or `$7E:E16B` (long). Vanilla, Magno, the five randomizer modes, an Ancient Cave and the three
conflict ROMs all contain the same two hits (`D2:A283` and `DD:9906`, inside compressed data, listed as benign); anything else is reported. `apply` warns on stderr when `monster_flinch` is strong/heavy and `verify` prints the hits
and exits 1 in that case. A synthetic `LDA $016B,X` in an otherwise vanilla ROM is detected. It is a byte-pattern scan, not a disassembly: an indirect access such as `(dp),Y` with `Y = $016B` built at run time would not be seen.

### 8.5 Not implemented, with the reason

* **Swing speed**: the hero object step runs once per five frames (`$56 == 3`) and the combat tick (gauge, charge, swing state) is inside it. A faster swing animation would need the hero step to run more often, which also doubles walk, hit tests and the
  gauge, or a rewrite of each weapon's animation script. No safe single-site data patch exists; `weapon_recharge` already removes the waiting after the swing.
* **MP regeneration at rest**: MP is changed only by spells, items and level-up in the ROM; there is no regeneration tick to scale. It would need new code in the hero step plus a rest detector (no pad input, no combat): possible as a companion runtime injection, not as a safe ROM patch here.
* **Charge buildup altered by magic**: a magic effect that changes charge speed would need a new buff bit read by the charge routine; the only free buff bits are used by statuses the UI shows. `charge_speed_up_bonus` (the Speed Up buff) and `charge_bonus_item_id` (equipment) are the supported hooks.

## 9. Launcher integration (data side, no launcher code touched)

`tools/gameplay/gameplay_menu.json` is generated by `python3 tools/gameplay/som_gameplay.py menu --out tools/gameplay/gameplay_menu.json` and follows the schema style of
`tools/companion/randomizer/presets.json`: `schema`, `generator`, `note`, `config_schema`, `groups` (Weapon / Enemies / Heroes), `options[]` with `key`, `label`, `type` (`enum`, `bool`, `num`), `default`,
`group`, `advanced`, `help`, enum `values[] {v, l}`, num `min/max/step/decimals/optional`, and `randomizer_conflicts` (the randomizer settings whose default hack overlaps the option), plus `presets[]` (`id`, `name`, `description`, `set`):

| Preset | Content |
|---|---|
| Vanilla | nothing (the output is a byte-identical copy) |
| Quick Combat | `weapon_recharge=faster`, `run_recharge=fast`, `charge_speed=faster`, `monster_flinch=strong` |
| Arcade | `weapon_recharge=instant`, `run_recharge=none`, `charge_speed=fast`, `monster_flinch=strong`, `hero_flinch=light`, `crit_multiplier=3`, crit bonus 30, `walk_speed=3` |

`gameplay_menu.json` types are the menu's; the option file for `apply` is `{"options": {...}}` with the same keys, `bool` as true/false, enums as strings (`crit_multiplier`, `walk_speed`, `weapon_level_rate` as integers; list in `apply.integer_enums`),
and an empty optional `num` left out. `tools/gameplay/presets.json` carries the same presets.

CLI path on a generated ROM (the patch is applied after generation, on a copy, never inside the repository):

```
som-dualscreen generate --config cfg.json --rom <US v1.0 ROM> [--out-dir D]          # prints the generated ROM path, e.g. D/<key>.sfc
python3 tools/gameplay/som_gameplay.py apply --rom D/<key>.sfc --options gameplay.json --out D/<key>.gameplay.sfc --on-conflict skip
python3 tools/gameplay/som_gameplay.py verify --rom D/<key>.sfc --patched D/<key>.gameplay.sfc --options gameplay.json
som-dualscreen push-random --serial <adb serial> --rom D/<key>.gameplay.sfc           # optional
```

The sidecar `<key>.sfc.json` of the generated ROM does not describe the gameplay patch; the launcher should store the gameplay option set next to its own config and key the patched copy by (generated ROM key, option set).
The generated ROM checksum is invalid (randomizer output), and `apply` keeps it untouched in that case. Companion direct control (NMI stub in WRAM) works on the patched ROM (6b, 8.1).
